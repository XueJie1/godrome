# 代码结构评估与优化建议

评估日期：2026-10-18。对象为当时的当前工作区，基于提交 `ac39a01`，包含已有未提交修改及 `internal/player/arena_linux.go`。本文记录评估结果与建议，不表示建议已经实施，也不替代产品规格或验收记录。代码行号是评估时的位置，后续以函数名定位为准。

## 结论与评分

**整体 7/10：底层模块比较扎实，应用层需要集中状态所有权和异步生命周期，适合逐项迁移。**

按 Go + MyGO 原生 UI + 进程内 libmpv、单进程、无数据库和有界内存的项目目标评价。评分是工程判断，不是自动化度量；文件长度、目录数量和接口数量不直接决定分数。

| 维度 | 评分 | 依据 |
| --- | --- | --- |
| 模块划分与封装 | 8/10 | 播放引擎、协议、封面、磁盘缓存、配置和 MPRIS 的职责相对清楚。 |
| 应用层职责分配 | 6/10 | `app` 同时管理视图、会话、请求、分页、喜欢状态和播放编排。 |
| 状态与并发所有权 | 6/10 | 已有主线程派发、取消和代次防护；部分资源生命周期和磁盘提交顺序仍分散。 |
| 测试与验证 | 8/10 | 有纯规则、模拟 HTTP、UI tester、音频和总线测试；部分验证直接操作应用内部字段。 |

单独看内部包约 **7.5/10**，应用层约 **6.5/10**。整体分数表达综合判断，不按包数量加权平均。

评估采用深模块原则：调用者通过小而明确的接口获得较多行为；复杂度、规则与验证集中在拥有它们的模块。接口也包括取消时机、调用顺序、错误处理和性能约束。

## 当前结构与值得保留的设计

实际主要调用关系如下；`session` 和 `library` 仍是目标模块，不能当成已经落地的结构。

```text
main → app（视图、页面请求、会话与播放编排）
         ├─ nav / equalizer：纯规则
         ├─ playbackState → queue → subsonic.Song
         ├─ subsonic.Client → net/http
         ├─ player.Engine → cgo 桥 → libmpv
         ├─ cover.Cache → 注入的封面获取函数
         ├─ appCaches → cache.Store × 2
         ├─ config → 配置文件 / 系统密钥环
         └─ mpris ← Snapshot / Controls
```

值得保留：

- **player 的模块深度较好。** 命令与事件流隐藏延迟初始化、native handle、属性转换、进度节流和销毁；单 worker 独占底层 handle，关闭时取消并等待退出。
- **封面处理有明确预算。** 两名 worker、32 个请求槽、去重、图片尺寸保护、位图 LRU 和容量限制集中在实现内部。
- **nav、equalizer 和队列规则容易独立验证。** 历史只保留页面参数和资源 ID，不保存整页数据或认证地址；队列替换复制输入切片。
- **协议请求的通用约束集中。** 认证、脱敏、TLS、超时、context、分页和响应大小限制由客户端处理。
- **config 和 MPRIS 的职责明确。** 配置白名单与系统密钥环分开；MPRIS 通过快照和回调隔离 D-Bus 的单位、信号与位置外推。
- **抽象数量克制。** 播放器真实实现、测试替身，以及缓存和获取函数的替换点有实际用途；不需要为每个包再增加一层公开接口。

## 同类项目参考

### Supersonic：最贴近的参考

Supersonic 同样使用 Go、原生桌面界面和 mpv。参考其实际实现中的两点：

1. `PlaybackManager` 集中高层播放操作，在界面与底层播放器之间处理队列和命令；底层播放实现不承担所有应用规则。
2. `mediaprovider` 使用应用自己的曲目、专辑等类型，播放流程不直接依赖 Subsonic 响应类型。

这些做法支持 Godrome 集中播放控制、引入小型曲目值模型。Supersonic 的多服务器、多播放器和丰富功能对应更大的接口，不应把整套结构直接搬入本项目。

参考源码：

- [PlaybackManager](https://github.com/supersonic-app/supersonic/blob/main/backend/playbackmanager.go)
- [MediaProvider 与应用媒体类型](https://github.com/supersonic-app/supersonic/blob/main/backend/mediaprovider/mediaprovider.go)

### Feishin：集中播放与队列状态

Feishin 的 player store 集中队列、循环、选曲和播放操作，可借鉴规则有固定归属的方式。其 Electron 进程通信、多播放后端和复杂队列超出 Godrome 当前需要；集中状态也不等于照搬一个很大的全局 store。

## 优化建议

以下涉及行为的路径来自静态核对；现有测试通过不代表这些组合已被覆盖。具体问题尚未逐项通过新增测试或真实桌面操作复现。

### 1. 优先：统一磁盘缓存提交顺序

位置：`internal/cache/store.go` 的 `Put`（124 行）、`Clear`（184 行）、`flush`（321 行）。

`Put` 在锁外 Rename，之后才检查 generation 并更新内存索引；`Clear` 重置状态后释放锁，再删除旧文件和扫描目录；索引快照也在解锁后写入。内存状态的锁没有统一文件系统操作的提交顺序。

存在以下交错风险：同一个键并发写入时，文件内容和索引中的 Size 来自不同写入；Clear 可能删除清空之后新提交的文件；较旧的索引快照可能最后提交。`-race` 不能发现这类文件系统语义问题。

建议保留当前对外接口。临时文件内容写入可留在锁外，将校验、目标替换、删除、索引状态更新集中到统一提交临界区；串行化索引提交，明确 Close 如何等待已有提交结束。

验收重点：受控交错的同键 Put、Clear/Put 和索引提交/Close 测试，同时核对实际文件、索引与 Stats。现有并发测试主要让不同 worker 写不同键，不足以覆盖这些顺序。改动规模中等，主要集中在 Store 实现与测试。

### 2. 优先：统一页面与请求生命周期

位置：`app.go` 的 `beginPage`（262 行）、`setupCovers`（347 行）、`searchNow`（859 行）；`internal/cover/cache.go` 的 `Get`（47 行）。

页面切换、搜索和设置页分别处理取消与资源释放，调用者必须理解多套顺序。搜索取消旧 pageCtx 后，仅在 covers 为 nil 时创建缓存；旧缓存可能继续绑定已取消的 context。Get 在 context 已取消时直接返回空，连已有位图也不会读取。

先统一进入、离开页面和开始请求的处理，区分页面资源与搜索防抖/请求的生命周期。随后让 session 拥有请求代次、取消、分页缓存和结果归属；app 保留当前帧快照与控件状态。不需要为具体客户端新增一个只有单一实现的接口。

验收重点：从已有封面的页面进入搜索、连续修改查询、离开搜索、进入设置、过期响应，以及取消后页面位图的释放。必须保留等待搜索时显示上一批结果的行为。改动规模中等。

### 3. 集中完整播放操作

位置：`playback.go` 的 `playbackState`；`app.go` 的 `onPlayback`（247 行）、`playCurrent`（909 行）；`media.go` 的播放控制方法（137 行起）。

playbackState 已集中队列移动与循环规则，但曲目来源解析、generation、加载、错误和快照仍由 app 管理。UI 与 MPRIS 分别组合“移动队列，再播放”等步骤，调用者仍需理解播放事务。部分加载中行为也由各入口自行决定。

建议把引擎、generation、队列、循环和播放快照集中到 playback，通过 Play、Next、Previous、TogglePause、Seek、Stop、事件处理与只读快照隐藏顺序。区分传输错误与音量、窗口可见性等控制错误，避免任意命令失败都改变播放状态。沿用已有引擎替身，先集中现有行为。

验收重点：同一状态下 UI、键盘与 MPRIS 的操作结果，过期 EOF、加载失败、循环和关闭。此项涉及播放，必须运行 `make test-audio`。改动规模中等偏大。

### 4. 让离线来源随本次结果返回

位置：`internal/subsonic/client.go` 的 `call`（273 行）；`app.go` 的 `finish`（290 行）。

客户端用全局 atomic stale 保存最近请求的来源，页面在 UI 消费结果时再读取。页面响应完成后，其他请求可能改变该标志；内存专辑页缓存也未保存自己的来源。atomic 避免数据竞争，但不能保证来源与结果对应。

建议在读操作返回值中携带来源，例如 `Result[T]{Value, Stale}` 或明确的附加返回值，和数据一起跨 dispatch；页面缓存同时保存来源。写操作不需要该字段。

验收重点：页面结果已返回、UI 尚未消费时另一个请求完成，以及返回内存缓存页面。改动规模中等。

### 5. 统一喜欢状态的事实来源

位置：`app.go` 的 `songLiked`（569 行）、`albumLiked`（579 行）、喜欢写入与 `noteStars`；`internal/subsonic/client.go` 的读缓存和 star/unstar。

喜欢状态同时存在于协议对象、会话 map 和缓存 JSON。当前读取优先接受旧对象中的 true，再查 map，明确的 false 因此无法覆盖旧 true。

可达路径是：在线读取已喜欢歌曲并缓存 → 成功取消喜欢 → 服务器网络不可达 → 离线重新加载同一曲库页。旧 JSON 中的 Starred 会重新进入歌曲对象，界面可再次显示已喜欢。该问题不应描述为“返回专辑列表再打开详情必然复活”，因为详情另有刷新路径。

建议用“未知、喜欢、不喜欢”的会话覆盖值；显式确认的结果优先于旧对象，noteStars 合并时也遵守该规则。后续再明确刷新和相关读缓存失效策略。

验收重点：成功取消后离线重载、喜爱页合并、失败回滚与快速连续操作的结果顺序。改动规模小到中等。

### 6. 逐步引入应用自己的曲目值模型

位置：`internal/queue/queue.go:3`、`internal/subsonic/client.go` 的 Song、`app.go` 的 `local` 和 `playCurrent`。

queue 依赖 subsonic.Song，本地文件也通过带 Path 的协议对象表示。协议模型承担了应用播放模型的职责，来源判断因此进入多个调用者。

建议引入小型 library.Track 值模型，先迁移队列和播放；远程响应在进入该流程时转换，本地 Track 直接构造。保留纯队列规则，不引入通用 Provider 框架或泛型容器。改动规模中等，可分步完成。

### 7. 让测试与验收通过稳定接口驱动

位置：`app_test.go`、`main.go:62`、`acceptance_main.go:117`。

部分测试直接设置 app 内部字段和 generation；验收入口直接读取状态，并复制窗口事件绑定。正式入口包含的 MPRIS、均衡器装配没有通过共享绑定进入验收入口，验证对象可能逐渐分叉。

在迁移 session/playback 时，把规则测试迁到模块命令与快照上，保留 UI tester 验证用户可见行为。让正式程序与验收共用窗口生命周期绑定，用小型只读诊断快照暴露必要测量值，不把所有字段导出。改动随对应模块迁移进行，避免一次改写整套测试。

### 8. 后续清理：明确 MPRIS 封面文件所有者

位置：`internal/subsonic/client.go` 的 `CoverPath`（395 行）。

缓存无法提供路径时，协议模块直接向临时目录写封面，缺少容量和清理所有者；备用文件名只取决于资源 ID，不同账号或服务器的相同 ID 可共用路径。

优先让已有有界缓存提供路径；缓存不可用时，可返回错误并省略桌面封面。若要求备用落盘，也应交给明确负责预算、命名空间和清理的存储模块。不要在协议实现里留下第二套无人管理的文件存储。改动规模小。

## 建议实施顺序

第一批先处理 Store 提交顺序和页面/请求生命周期，两项分开变更，分别补覆盖具体顺序的回归测试。它们都对应当前可达路径，且能为后续迁移建立可靠基础。

随后集中 playback，再处理响应来源和喜欢状态，逐步迁移 Track；测试接口与窗口装配随相关模块迁移。响应来源和喜欢状态也可作为独立的小步修正提前处理，不必等待大模块重构。最后清理备用封面存储。

本顺序表达优先级，不是已获执行授权的重构任务。正式依赖方向、状态归属和迁移约束继续以 [ARCHITECTURE.md](../ARCHITECTURE.md) 为准；实施时一次迁移一项职责，保持现有行为并同步相应文档。

仅按页面拆小 app.go 可改善阅读，但不能代替状态所有权迁移。当前无需新增后台进程、数据库、通用事件总线，或为每个包引入公开接口；平台差异和不同缓存策略也不必为消除表面重复而合并。
